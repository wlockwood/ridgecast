# Adaptive LiDAR compilation and computer calibration design

Status: implemented under the subsequent execution request; final qualification evidence is recorded in the [implementation plan](../plans/2026-10-07-lidar-compilation.md). The prototype results below are historical feasibility evidence.

## Intent and evidence

Reduce the waiting time for batches of 100 or more LiDAR surface requests and make Performance & Calibration describe this preparation work. Choose execution from measured CPU/GPU performance on the user's computer, rather than the development computer's hardware ratio. Preserve correct terrain, reusable caches, cancellation, and a responsive desktop.

The standalone prototype in `tools/lidar-surface-bench/` measured a six-job, 2048x2048 numeric batch at 1.143 s CPU versus 0.531 s pipelined CPU decoding/GPU compilation on the RTX 4070 Ti, a 2.154x gain. The integrated Radeon achieved only 1.070x for that batch. On individual large crops it beat four CPU workers by approximately 1.28x but lost to sixteen workers, taking approximately 31% longer. GPU startup and timing variation matter. These measurements use a partial cached acquisition and exclude production support metadata, compression, publication, and sustained disk I/O; they are feasibility evidence, not expected application speedups.

Source at design time: `src/performance.rs::benchmark` explicitly disables LiDAR. `WorkFamily` and its calibration rates concern propagation and Site Finder. `src/engine/itm_dsm.rs` serializes preparation with `PREPARE_LOCK`; `surface.rs::build_surfaces_from_plan` decodes nodes sequentially. It also preserves acquisition-wide ground classification, node rollback, support evidence, and corruption recovery. `publish_surface` validates staged outputs before making them visible. The status in `src/link_solve.rs` counts requests, which can differ greatly in cost.

## Recommended approach and alternatives

Implement a shared production surface compiler, improve the CPU baseline, then add GPU execution and a bounded CPU/GPU pipeline. Calibrate that same pipeline with reproducible local fixtures and use the results per workload size and available worker count. Instrument the complete path before choosing compression or storage optimizations.

A forced GPU backend is simpler but regresses small jobs and machines with relatively strong CPUs. CPU-only optimization is valuable and ships first, but leaves the measured opportunity on discrete GPUs unused. A generic CPU/GPU/disk score cannot predict this pipeline: decoding, filling, transfers, and publication have different scaling and cache behavior.

## Compiler and batching

Keep native LAS/LAZ validation, projection, polygon filtering, and f64 coordinate-to-cell mapping on CPU. Independent EPT nodes may decode in parallel into admitted, transactional sparse cell aggregates. Retain DSM maxima, classified-ground minima, unclassified minima, saturating counts, and direct support separately. A failed node contributes no measurements. Merge successful nodes in plan order; determine classified-ground availability across the acquisition before selecting its DTM. Preserve the existing sequential/journal path when staging does not fit. A single large LAS/LAZ stream remains sequentially decoded initially.

The CPU compiler remains the correctness reference. The GPU compiler handles numeric bin aggregation, gap filling, bounded interpolation, and obstruction generation, with support and density semantics preserved. GPU support updates must be implemented or replayed faithfully on CPU and included in total timings; a numeric-only compiler is insufficient for production. Use the initialized compute device through a narrow internal handle, with lazily created surface pipelines and reusable admitted buffers. Do not require propagation-model compatibility for surface compilation.

Start with one CPU preparation producer and one GPU consumer, with one queued work item and explicit byte admission. They work on successive independent crops while finalization/publication proceeds through a bounded stage. This uses CPU and GPU simultaneously. Do not initially add concurrent CPU-only surface compilers alongside the GPU; decoding, support work, and compression already consume CPU and must share its worker budget. Do not increase the number of builds in flight just to raise utilization percentages.

Replace the broad preparation lock with cancellable per-request single-flight ownership only after shared memory admission exists. Different requests may overlap expensive work; identical requests join one build. Lock only short shared cache/index updates. Publication stays atomic per surface, and completed surfaces survive restart and cancellation of later work. Recheck covering-cache reuse after acquiring ownership. Keep captured source plans, download generations/triggers, and settings on all worker paths. Frozen coverage cache-hit contexts must remain frozen.

## Computer benchmark

Add a separate LiDAR calibration domain; do not express surface work as propagation units or pool surfaces of different sizes into one rate. Preserve existing CPU/GPU propagation measurements and their geometry validation.

Use deterministic locally generated compressed LAS/LAZ fixtures with ground, roofs, sparse holes, classification transitions, and invalid-node fixtures for correctness. No downloads or dependency on the developer's geodata. Measure 256x256, 1024x1024, and 2048x2048 grid classes at 0.9144 m spacing, with sparse and dense point distributions. Run CPU and GPU variants on identical inputs, alternate paired ordering, and include single-job and six-job cohorts. Quick targets 30 s of measurement and Extended 120 s, plus reported setup; stop admitting new cohorts at the deadline and mark unmeasured combinations unavailable. Require at least five complete paired trials for a routing recommendation. Extended targets seven and sweeps worker counts `1, 4, 8, 16, N`, clipped/deduplicated against the allowed workers; Quick compares one worker and `N` on the classes that fit its budget. `N` is the captured permitted CPU allowance, bounded by available parallelism and the existing prototype's 64-worker ceiling. Do not hard-code the development run's sixteen workers. Memory admission can allow fewer simultaneous native decoders than the pool's worker count.

Report separate timings for first use/setup, cached input reads, native decode/projection, aggregation, numeric fill/interpolation, support work, upload/dispatch/readback, encoding/compression, writes/sync where requested, staged validation/reload, and complete wall time. Overlapping stage durations do not add to wall time. GPU timestamp queries are optional diagnostics, never the selection metric. Warm and first-use observations must be distinguished; do not describe a sum of warm time and setup as a measured cold run.

Storage tests run in a unique scratch directory on the active surface-cache filesystem, with at most 256 MiB of benchmark files. Compare in-memory compressed input, filesystem input, and full production artifact write/reopen validation. Include many-small-file reads and report bytes, file count, throughput, write completion semantics, and observed reopen cache state. Compression comparisons use zstd levels 3 and 9 with representative surface bytes, including support artifacts. Reopened reads may hit the OS page cache: label them warm or cache state unknown. Do not flush the OS cache or claim a physical-device cold test. Optional OS counters may support diagnosis; unsupported counters must not prevent calibration. NVMe alone does not establish that storage is fast enough, and file API time alone does not identify hardware saturation.

Persist bounded, validated LiDAR records alongside existing records with Serde defaults. Scope by machine/build, compiler and fixture revision, adapter/vendor/device/backend/driver identity, worker budget, grid/point-density envelope, execution mode, and storage identity for filesystem measurements. Retain at most 64 LiDAR probe records and the existing 128 propagation records within the existing 1 MiB file bound. Missing/unknown storage identity makes its measurements session-only. Hardware/build/cache-volume changes make matching records inapplicable; canceled or failed calibration preserves prior records. Preparation results use existing cache freshness checks, independently of calibration.

## Selection, progress, and failure

Auto uses CPU without matching valid calibration. Select GPU only if at least five paired trials establish a conservative total-time improvement of 15%: compare the fastest CPU cohort with the slowest GPU cohort, including mandatory support and I/O work. For first-use batches include measured required initialization once; do not charge an already initialized device again. Small or mixed batches outside the measured envelope stay CPU unless their individual classes are qualified. Select the CPU worker configuration from complete elapsed-time comparisons, not core count. A GPU chosen for Site Finder does not imply a GPU chosen for surfaces.

Monitor actual build timings without benchmarking duplicate full jobs during normal operation. Suspend a GPU recommendation for the remaining batch when five matching observations have a median above the stored CPU upper-time baseline; keep observations separate from controlled calibration. On GPU errors, release buffers and retry the same immutable input on CPU if memory admission permits. Report the fallback and never store CPU work as a GPU measurement. Device loss disables that GPU path for the session. Cancellation is not a CPU retry; no stale generation publishes results. Lack of sufficient GPU limits or precision eligibility uses CPU. A numeric mismatch during qualification disables GPU for that compiler/adapter combination.

Extend the existing status with reused/building/completed/failed counts, active stage, selected backend, and a preparation ETA range when matching calibration or sufficient matching completed work exists. ETA weights request grid cells, accepted-point estimates where known, and work class; it is not `remaining requests * one average`. Label unmatched estimates rough and acquisition/download time separately. Emit bounded/coalesced progress, including before a long first build. UI only queues/polls; all controls have tooltips. Keep lower-level timings in benchmark details rather than ordinary calculation flow.

## Correctness and release gates

- Exact NoData masks, georeferencing, classification choices, saturated return counts, density, failure regions, donor membership, support methods, and provenance must match CPU semantics. GPU elevation/obstruction differences must be at most 0.001 m on qualified fixtures, with representability and sentinel checks before dispatch. Values outside the supported numerical envelope use CPU.
- Corrupt/malformed native input must preserve bounded allocation, node rollback, corruption retry, and source failure reports. Missing data must never become open ground. Test classification discovered in a later/disjoint node, sentinel elevations, withheld/noise returns, and overlapping crops.
- Shared CPU/GPU host budgets include native codecs, staged node aggregates, support, readback, encoder and reload overlap; GPU buffers respect actual device limits and a conservative 256 MiB surface allocation budget initially. Device limits do not reveal free VRAM. Low-memory machines fall back to sequential work. Cancellation while blocked on channels/ownership must wake and release reservations.
- Do not invalidate valid prepared CPU surfaces merely because a GPU becomes available. Preserve existing cache formats and freshness semantics when the output contract remains equivalent; any deliberate algorithm change needs the existing algorithm-version migration and explicit review.
- Qualify the full path on discrete and integrated GPUs, CPU-only configurations, different worker budgets, memory restrictions, and slower storage. The prototype's six-job speedup is not a shipping threshold for other machines. Auto enables a class only when that machine's full-path gate passes.
- Finish with a 100-request production preparation qualification, successful second-run cache reuse, cancel/restart recovery, frozen coverage-cache regression, and an idle/responsive UI. Retain raw results and fixture/build/hardware identities.

## Scope boundaries

This release does not implement GPU LAZ decompression, GPU RF propagation changes, unbounded job concurrency, compulsory hardware telemetry, an all-machine performance score, or an unbounded persistent decoded-point cache. Cross-request point-cloud fan-out can follow if stage timings show repeated decoding dominates after this work. Compression level changes require full-path evidence and remain specific to newly compiled LiDAR artifacts; general terrain-cache policy is unchanged.
