# RidgeCast 0.4.0

Changes since October 13, 2026, including improvements made later that day.

## Summary

RidgeCast 0.4.0 makes large radio networks easier to explore and less expensive
to calculate. The performance and link-view improvements grew out of working
on a 322-node network with coverage spanning four U.S. states and parts of
British Columbia. New link views help identify long, strong paths and connections
between well-connected groups; a new node ranking highlights radios with short
hop counts to the wider network. Expanded LiDAR sources and contextual guides
make detailed terrain and clutter planning more accessible.

Behind these changes, RidgeCast reads smaller portions of large terrain files,
shares work between transmit and receive calculations, reuses downloaded and
calculated data, and keeps more preparation off the interface thread. Recorded
tests show substantial gains in specific workloads, detailed below; actual
savings depend on hardware, data and cache reuse. Imports, map refreshes,
download reporting and file handling also receive reliability fixes.

## New features

- **[Configurable link views](../reference/link-view-settings.md):** Color and
  filter links by fade margin, distance, or Long and Strong, which combines
  distance with signal headroom. Adjust palettes and scales, highlight selected
  sites' links, and carry the presentation into coverage image exports.
- **[Connectivity priorities](../concepts/connectivity-priorities.md):**
  Connectivity Potential highlights links with substantial network connectivity
  on both sides. Harmonic Connectivity ranks radios by how many others they can
  reach in few hops. Both use qualifying two-way links; neither predicts measured
  reliability or construction value.
- **[Expanded LiDAR sources](../reference/lidar-source-catalog.md):** Browse
  national and state collections and acquire supported point clouds or surface
  rasters directly. Availability depends on location, compatible ground data and
  provider access; the picker explains sources that cannot yet be used.
- **[Contextual guides](../how-to/use-companion-guides.md):** Open task-specific
  help beside planning tools without interrupting your work. Each guide has an
  independent preference for opening automatically next time.
- **[Save partial link calculations](../concepts/link-result-cache.md):** Save
  completed directions during an unfinished or canceled calculation. Reopening
  with matching radio and model settings reuses recorded outcomes and calculates
  missing paths. Use Recalculate All Links to refresh predictions against newly
  downloaded terrain or clutter.
- **[Settings-save diagnostics](../how-to/troubleshoot.md):** Visible feedback
  explains failed settings saves, with diagnostic details to help identify
  permissions or file-access problems rather than silently losing preferences.

## Performance optimizations

Estimates below describe the named work, rather than an overall application
speedup. Measurements used the development computer: a 16-core Ryzen 9 9950X
with NVMe storage. [Benchmark details and limitations](../reference/performance.md)
explain the workloads.

- **Map panning and zooming:** A synthetic 36-tile viewport filled in 153 ms
  versus 306 ms, about 2× faster. CPU rendering alone improved about 14×.
  Recent tiles are reused; these tests exclude downloads, disk decoding and live
  GPU drawing.
- **[Terrain memory and reads](../reference/terrain-subtile-access.md):**
  Supported tiled elevation files decode only needed blocks. One 500-sample
  path retained about 20 MB instead of a 467 MB full elevation array: roughly
  96% less decoded terrain memory. Wide-area coverage saves less; downloaded
  files remain the same size.
- **Network link calculations:** Opposite directions share terrain sampling,
  potentially halving that duplicated stage while retaining separate radio
  budgets. Early screening avoids detailed preparation for clearly unsuitable
  paths. Overall solve-time savings have not been measured.
- **Coverage calculations:** Transmit and receive predictions share path
  preparation; nearby sites reuse terrain, and unchanged grids skip preparation.
  This should reduce repeated decoding, disk reads and calculation time, with
  the greatest benefit in overlapping or repeated runs. No overall percentage
  is established.
- **LiDAR preparation:** CPU work overlaps within the memory allowance.
  A small, warm-cache experiment preparing 100 products took 0.65 s with
  32 workers versus 1.20 s with two: about 1.8× faster. This single-run comparison
  excludes downloads and does not predict dense-survey throughput.
- **Disk and download reuse:** Shared source files and compatible prepared
  crops avoid duplicate transfers and rebuilding. Reopening the 100-product
  LiDAR test required zero rebuilds. Spatial readers can fetch only relevant
  portions of supported sources; there is no measured general reduction in
  disk footprint.
- **Interface responsiveness and memory management:** Large lists, overlays,
  exports and cache inventories use background work and bounded updates.
  Automatic decoded-data budgets adapt to available RAM, and shared terrain
  allocations count once. Expect fewer pauses and redundant allocations;
  interface latency has not been benchmarked.

## Bugfixes

- Bulk coordinate imports preserve complete site names, including spaces.
- Failed Radio Mobile imports leave the existing network intact.
- Radio Mobile imports avoid conflicting system identifiers and invalidate stale links.
- Terrain shading remains visible while newly available source data refreshes.
- Validated water tiles survive cache reloads, preserving consistent terrain masking.
- Radio, terrain and antenna-height controls honor the selected display units.
- Selected-site detail controls retain their state when switching between nodes.
- LiDAR progress reports provider waits, local work and completed tiles more consistently.
- Download retries respect provider cooldowns and limits after redirects.
- Interrupted LiDAR cache updates preserve storage accounting and existing data.
- Exports avoid overwriting existing files and roll back incomplete output groups.
- Malformed terrain files cannot request unbounded decoder allocations.
- Adding sites frames the map with surrounding geographic context.
